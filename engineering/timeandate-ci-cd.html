How I designed the Time And Date release pipeline

A GitHub Actions and Cloudflare case study in building once and deploying the bundle QA tested.

By Rahul Shinde · Time And Date · CI/CD design

Time And Date is a small app, but I wanted a production release to be traceable. If I saw something unexpected on the live site, I wanted to be able to work backward from the deployed files to a candidate and then to the commit that built it.

World Clocks and Timer both run from static web files, so I could keep the infrastructure small. The release pipeline still had to answer the questions I’d expect on a team: which commit passed CI, which bundle QA tested, and which build is live? Time And Date on GitHub

The architecture in one view

Pull request → CI checks → merge → CI on the merged commit

Verified commit → build and package → Cloudflare QA → GitHub prerelease

Selected prerelease → production approval → deploy the same bundle → verify live → GitHub stable release

A merge can happen as soon as the change is ready. A production deploy can wait until someone has tested and approved a specific bundle.

CI on the commit that will ship

GitHub Actions runs CI on pull requests and on pushes to main and release branches. It lints the workflow files, installs dependencies from the lockfile, runs the tests, and builds the app. PR checks run with read-only repository access and without Cloudflare deployment credentials. That makes them appropriate for contributions to a public repository.

I chose to verify the actual release SHA against a successful push CI run. The commit that lands after a merge can differ from the revision that passed PR checks. The release planner verifies the SHA it will build, and it requires that the commit be reachable from main or a maintained release branch. Branch rules can make the CI check a merge requirement. The release check then applies that same standard to the exact source selected for deployment. CI workflow

What goes into the release bundle

The release workflow runs from main. Its source can come from main or a release branch. That separation lets me use the current release workflow to build a specific, older maintenance commit when needed.

For a routine candidate I leave the source SHA and tag blank. The workflow pins the main commit at dispatch and uses that commit’s package.json version to choose the next RC tag. For example, version 0.2.0 starts at v0.2.0-rc.1. When I need a particular release branch commit, I can supply its full SHA. I can also specify a candidate tag explicitly.

The build produces a static bundle and two forms of evidence:

  • A SHA-256 checksum lets the workflow verify that the archived bundle’s bytes match the expected digest.
  • A build manifest inside the bundle records the source SHA and candidate tag. Once the site is deployed, /build-info.json lets me compare the live build with the one I meant to deploy.

After automated QA succeeds, GitHub publishes the candidate as a prerelease with the archive and checksum. Production can retrieve that bundle later without relying on the original job’s temporary artifact. I treat a published tag and its bundle as fixed. If the source changes, I cut a new candidate. The checksum provides integrity checking, and control over tag and release writes determines who can publish a trusted bundle. Release workflow

Cloudflare deployment and QA

The Wrangler configuration defines two Workers with Static Assets, one for QA and one for production. GitHub Actions deploys through Wrangler, using a token held in the appropriate GitHub environment. The repository keeps the Worker configuration separate from the deployment credentials. Each environment also has a public HTTPS URL for verification. Cloudflare Workers Static Assets · Project setup

After Wrangler finishes, the smoke test calls the public QA URL. It checks the candidate tag and SHA in the live manifest and verifies that direct links to World Clocks and Timer return the app shell.

A browser check covers what those requests miss. For example, with World Clocks, I can open a shared board in a fresh browser session and check that the right cities appear in order. For Timer, I can set a countdown in a different timezone, check the tab title, reload, and confirm that the timer completes. The manual check starts by matching the candidate tag and SHA in the live manifest. That’s particularly useful with a shared QA Worker, where another release can replace the build between reviews.

One shared QA Worker keeps the design manageable for a solo project. For a team testing multiple changes in parallel, I’d consider per-PR previews for early feedback and keep a dedicated candidate environment for the actual release decision.

Approve an artifact and promote it unchanged

Promotion requires an explicit, published RC tag. I deliberately kept automatic selection for building a candidate and explicit selection for promoting one. At build time, the latest tested commit on the intended line is a reasonable default. At promotion time, the important fact is which candidate QA reviewed.

The release plan shows the selected tag, source SHA, and checksum. With a required reviewer configured for the GitHub production environment, the deployment job waits at GitHub’s Review deployments step before it can use the environment’s Cloudflare credentials. The reviewer can check the plan against the QA results before approving. On a team, I’d use an independent reviewer when that fits the risk and release cadence. GitHub deployment reviews

Once approved, production verifies and deploys the saved web bundle. The workflow then checks the public production URL before publishing the stable GitHub release with the same assets. The manifest still identifies the RC because the bundle hasn’t changed. The stable release notes link the two versions.

Rebuilding for production would let me inject different build-time settings. The cost is that I’d be deploying a fresh output after QA. Time And Date can use identical static assets in both environments, so I keep the differences in the deployment target and credentials. For a larger system that needs environment-specific configuration, I’d assess which settings can be applied at runtime and how to verify them separately.

Give features, patches, and recovery the same release path

A feature normally gets its candidate from main. When a version needs to stabilize while main moves ahead, I can cut a maintenance branch from the relevant tag and build the next RC from a tested commit on that branch. A production patch can start the same way from the last shipped tag. Both use the same build, QA, and promotion gates. I can keep release branches for as long as the version needs active maintenance.

I also included a rollback operation. It selects an existing stable release, verifies the saved artifact, goes through the production approval gate, and redeploys that artifact. Restoring a static site this way is practical because the pipeline preserves the old bundle. Systems with database migrations or stateful services need a broader recovery design, including compatibility between old code and current data.

The project has a separate manual workflow for Android debug and iOS Simulator builds. That division reflects the deployment model. A Cloudflare deploy changes what web users receive. A mobile release has its own signing, distribution, and rollout requirements. Release runbook · Mobile build workflow

What I’d carry into another project

On another project I’d first ask what the team needs to verify before it can release, and what it needs to find during an incident. The answer would shape the pipeline more than the choice of hosting provider. For this app, that means I can open a release, find the commit and bundle it was built from, and check whether production is serving it.
