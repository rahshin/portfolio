What to do when a Time And Date release needs a second try

A failed first QA check, a worked RC backport example, and the decisions I’d make when a release stalls.

By Rahul Shinde · Time And Date · Release operations

On the first QA deployment, the verification step reported ENOTFOUND after eight attempts. I wondered whether the first run needed an existing build-info.json. The workflow showed that the manifest is generated during the build. The error was earlier in the request: the runner couldn’t resolve the hostname to ask for the file.

DEPLOY_URL tells verification which address to call. To use a custom hostname, I have to attach it to the QA Worker and check that it resolves. The Worker’s workers.dev address is another option. Cloudflare Custom Domains

The rest of this post uses worked examples and recovery procedures. The version numbers are illustrative. Time And Date release runbook

The pipeline builds one web bundle, deploys it to QA, and attaches it to the prerelease after automated verification. Promotion selects that prerelease and deploys the same bundle after approval. The examples assume that design. Time And Date release workflow

A QA checklist for the next candidate

The automated smoke test fetches /build-info.json and checks that its candidate tag and source SHA match the bundle. It also requests both app routes and confirms they serve the app shell. It retries briefly to allow for deployment propagation. This verifies reachability, routing, and build identity. A successful HTTP response alone cannot tell me whether the JavaScript rendered correctly or whether the countdown works.

Here’s the checklist I’d use after the automated QA job passes:

  1. Identify the build. Open the QA run and match the candidate and SHA against the live manifest. QA is a shared Worker, so a later candidate may have replaced the one I intended to test.
  2. Exercise World Clocks. Add, remove, and reorder cities. Open a copied link in a fresh browser session and check that it restores the same cities in the same order. Compare cities on opposite sides of midnight to verify the date as well as the time.
  3. Exercise Timer. Start a short countdown in a timezone different from the device’s. Check the display and tab title, reload to check persistence, and wait for completion. For timezone changes, also test a daylight saving transition and confirm ambiguous or nonexistent local times are handled clearly. Check a longer countdown that crosses a month boundary.
  4. Check the affected platforms. Try the changed path at desktop and phone widths and with the keyboard. If I changed shared web code used by the Capacitor apps, run the relevant native build and exercise the affected flow on a device or simulator. Browsers can throttle background tabs, so I check that the title catches up when I return.
  5. Leave evidence. Record the candidate tag, source SHA, browser or device, tested cases, and any unresolved issue in the review or release notes. Add a regression test for any defect the candidate fixes.

Separate preview URLs for every PR would make parallel reviews easier. The shared QA Worker keeps this project simpler, with the tradeoff that reviewers need to verify which build is live before signing off.

Worked release examples

A new feature is ready

A normal feature follows a PR to main, push CI, and a candidate for the intended version. If the change belongs in the next planned release, I include it in the next candidate and test the whole bundle again. Building one RC per reviewed batch keeps QA focused. Cutting one for every commit would give faster feedback but create more artifacts and more work for a shared QA environment.

QA finds a bug and main contains everything I want to ship

I merge the fix into main, wait for push CI, and cut the next RC for the same version. If RC1 was v0.2.0-rc.1, RC2 is v0.2.0-rc.2. RC2 is a full build of the new commit, so it includes the fix and the other intended changes on main. I recheck the bug and the areas affected by those changes. RC1 stays intact.

QA finds a bug after unrelated work has landed on main

I cut release/0.2 from the v0.2.0-rc.1 tag. The fix is already on main, so I cherry-pick just the fix onto a branch based on release/0.2 and open a PR into that release branch. If the fix relies on the new work, I adapt it to the RC code and test it there. After the PR merges and push CI passes, I run candidate from workflow ref main, enter v0.2.0-rc.2, and provide the tested release-branch SHA. Leaving the SHA blank would pull in the very changes I meant to leave behind.

An RC tag gives me a fixed snapshot. The maintenance branch gives me a place to keep fixing that release. Cutting the branch early gives QA a clear scope but adds backport work. Cutting it only when main diverges keeps routine releases light.

A production bug needs a patch or a hotfix

If production is on v0.2.0 and main is already headed toward 0.3.0, I create release/0.2 from the shipped tag if that branch does not exist. I land the fix there, wait for push CI, and dispatch from main with the tested SHA and explicit tag v0.2.1-rc.1. I verify it on QA before promoting. If the fix originated on the maintenance branch, I forward-port it to main.

For a severe outage, a known-good rollback can restore service faster than creating a hotfix. I still need to check whether the previous build can serve current users successfully. That question gets more important if the app adds data storage, migrations, or an API later.

An older line needs a release after 1.0.0 ships

Starting from v0.6.0, I use release/0.6 and v0.6.1-rc.1 for a bug fix, or release/0.7 and v0.7.0-rc.1 for a compatible feature. I create the branch when needed, merge the change there, and use browser tests that match that version of the app. Once push CI passes, I dispatch from main with the explicit candidate tag and tested SHA.

QA can serve the older candidate while production stays on v1.0.0. Promoting the candidate replaces the live web app on the shared production target. To restore the exact shipped v0.6.0 bundle, I use rollback. Supporting both versions in production would require separate deployment targets.

A major change is coming

I write release notes for user-visible changes and use Major release with a blank tag to start or continue the next major RC line after the latest stable release. I confirm the selected tag and source in the run summary. When a major change affects saved links or timer state, I test upgrades from the previous stable version.

A dependency, credential, or mobile toolchain changes

A dependency update goes through review, lockfile-based CI, and a candidate when it affects the web bundle. A Cloudflare token rotation is an environment change. Replace the credential, verify in QA, and confirm production still has the right account and permissions. If a credential is exposed, revoke it immediately and audit the affected deployments and release assets before resuming.

Mobile workflows produce a debug APK, an unsigned iOS Release Simulator ZIP, and a privately signed non-debug Android APK for sideloading. Store releases use separate signing and distribution. Web promotion and rollback replace static assets on Cloudflare. An installed native app is updated through its own distribution channel. Mobile build instructions

What I do when the pipeline fails

  • Planning rejects a tag or source SHA. Check the inputs and resolved values in the run summary and read the plan job’s error. A malformed or existing tag and a source commit without successful push CI need different fixes. Pin the exact tested commit before retrying.
  • The build or tests fail. Fix the code or toolchain, get CI green on the corrected commit, and cut a candidate. An infrastructure failure before publication can be retried with the exact same tag and source if that tag is still unused.
  • The bundle or checksum is missing or wrong. Stop before deployment. Check that both assets came from the same trusted release. Recover the original verified pair or cut a new candidate. A checksum catches an accidental byte change. A publisher with write access could replace both files, so protecting tags and release assets matters too.
  • Cloudflare uploads the build but smoke tests fail. DNS errors point to the hostname. HTTP errors point to the public route or access policy. A valid manifest for the wrong build points to the wrong Worker or an older active deployment. I inspect the live endpoint and Wrangler output before choosing a retry.
  • Approval is delayed or rejected. Leave production as it is while I resolve the concern. If the candidate needs a code change, cut a new RC. Before approving an older candidate, confirm it’s still the intended version. The workflow checks the candidate type and whether the matching stable tag exists. It doesn’t automatically reject every older version. Release runs share a concurrency group, and a new pending run can replace an older pending run, so I dispatch one release at a time.
  • Production changed but the workflow failed afterward. Check the live manifest and the GitHub release separately. A smoke failure can happen after Wrangler has already changed the live site. A publish failure can happen after smoke tests pass. In the latter case, inspect whether the stable tag, release, or assets already exist before retrying. A partial GitHub release may need reconciliation rather than another deploy.
  • A verified release later breaks. Dispatch rollback with a known-good stable tag. It goes through production approval, redeploys the saved bundle, and verifies live identity. Keep the failed release for diagnosis. Follow with a patched candidate when ready.
  • A service outage, planned retirement, or platform move changes the rules. During an outage, check what’s actually live and preserve the promoted asset and run evidence. For a planned move, verify the same bundle on the new target before switching traffic and keep a reversible DNS cutover. To retire the app, stop deployments, remove the public routes when ready, revoke credentials, and retain release records for as long as they’re useful. These are operator procedures, not automated jobs in this project.

What to verify before approving

For production, I select a specific published QA candidate. The release plan shows its tag, source, and checksum. With the production environment configured for required reviewers, GitHub pauses the job and offers Review deployments → Approve and deploy. I can see what I’m approving before the deployment job gets its credentials. A solo maintainer can allow self-review. An independent reviewer gives the gate more value when another maintainer is available. GitHub deployment reviews

Before approving a rerun, I’d check which build is live and whether the intended release already exists. The candidate tag and SHA in the live manifest tell me what Cloudflare is serving. The GitHub release and its assets tell me how far publication got. Those checks narrow down where to resume.
